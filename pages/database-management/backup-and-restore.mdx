# Backup and restore

Memgraph uses snapshots and WAL to ensure the [durability](/fundamentals/data-durability) of the stored data.
Learn how to safely backup and restore your data.

## Create backup

Follow these steps to create database backup:

<Steps>

{<h3 id="create-a-snapshot" className="custom-header">Create a snapshot</h3>}

  If necessary, create a snapshot of the current database state by running the
  following query in `mgconsole` or Memgraph Lab:

  ```cypher
  CREATE SNAPSHOT;
  ```
  The snapshot is saved in the `snapshots` directory of the data directory
  (`/var/lib/memgraph`).

{<h3 id="lock-the-data-directory" className="custom-header">Lock the data directory</h3>}

  Durability files are deleted when an event is triggered, for example, exceeding
  the maximum number of snapshots.

  To disable this behavior, run the following query in `mgconsole` or Memgraph
  Lab:

  ```cypher
  LOCK DATA DIRECTORY;
  ```

{<h3 id="copy-files" className="custom-header">Copy files</h3>}

  Copy snapshot files (from the `snapshots` directory) and any additional WAL
  files (from the `wal` directory) to a backup location.

  If you've just created a snapshot file there is no need to backup WAL files. 

  To copy the snapshot files from the Docker container first check the container
  ID by running `docker ps` then run the following command:

  ```bash
  docker cp CONTAINER_ID:/var/lib/memgraph/snapshots/SNAPSHOT_FILE SNAPSHOT_FILE
  ```

  `CONTAINER_ID` is the ID from `docker ps`, and `SNAPSHOT_FILE` is the
  snapshot's file name.

{<h3 id="unlock-the-data-directory" className="custom-header">Unlock the data directory</h3>}

  Run the following query in `mgconsole` or Memgraph Lab to unlock the
  directory:

  ```cypher
  UNLOCK DATA DIRECTORY;
  ```

  Memgraph will delete the files which should have been deleted before locking and
  allow any future deletion of the durability files.

</Steps>

## Restore data

Restore a snapshot to a running Memgraph instance using the RECOVER SNAPSHOT command:

```cypher template
RECOVER SNAPSHOT path=literal ( WITH CONFIG configsMap=configMap ) ? ( FORCE )? ;
```

Before modifying the local data directory, Memgraph will move all existing WALs and snapshots to a hidden
`.old` directory. This directory is reused for subsequent recovery operations, meaning **only a single backup
is maintained at any time**. Files already present in the `.old` directory will be deleted before moving
the current files, ensuring only the most recent backup is preserved. By default, snapshots are stored in the local directory `/var/lib/memgraph/snapshots/`.

Snapshots can be recovered from:
- Local filesystem - absolute or relative paths
- S3-compatible storage - s3://bucket/path/to/snapshot
- Remote servers - http://, https://, or ftp:// URLs

### Local filesystem

```cypher template
RECOVER SNAPSHOT "/path/to/snapshot";
```

Use absolute paths when possible. Relative paths are resolved from the Memgraph execution directory.
Memgraph copies the snapshot to its local snapshot directory, so ensure the file has appropriate read permissions.

If not, you might encounter the following error:

```plaintext copy=false
Failed to copy snapshot over to local snapshots directory.
```

### S3-compatible storage

Provide AWS credentials using one of these methods (in order of precedence):

| Method                | Example                                                                            |
|-----------------------|----------------------------------------------------------------------------------- |
| Query config          | `WITH CONFIG {aws_region: ..., aws_access_key: ..., aws_secret_key: ...}`          |
| Environment variables | `AWS_REGION`, `AWS_ACCESS_KEY`, `AWS_SECRET_KEY`, `AWS_ENDPOINT_URL`               |
| Runtime settings      | `aws.region`, `aws.access_key`, `aws.secret_key`, `aws.endpoint_url`               |

Example:
```cypher
RECOVER SNAPSHOT "s3://my-bucket/snapshots/backup.snapshot" WITH CONFIG {'aws_region': 'eu-west-1', 'aws_access_key': '...', 'aws_secret_key': 'secret'};
```

### The FORCE flag

If the instance is not freshly started, add the `FORCE` flag to your command:

```cypher template
RECOVER SNAPSHOT "/path/to/snapshot" FORCE;
```

This will clear all existing data before applying the snapshot.

<Callout type="info">

`RECOVER SNAPSHOT` is also the primary cure for a **broken** database — one that
failed durability recovery on startup and came up empty because
[`--storage-allow-recovery-failure`](/database-management/configuration) was
enabled. Running it against the broken database loads a known-good snapshot,
clears the broken state, and leaves the durability directory in a clean state
that recovers normally on the next restart. See
[recovery failure handling](/fundamentals/data-durability#recovery-failure-handling)
for the full set of restoration paths.

</Callout>


In order to query the snapshots currently present in the local data directory,
execute the query:

```cypher
SHOW SNAPSHOTS;
```

Its results contain the path to the file, the logical timestamp, the physical
timestamp and the file size.

As of Memgraph v3.5, the `SHOW SNAPSHOTS` query does not return information regarding the next scheduled snapshot.
A special query has been added:
```cypher
SHOW NEXT SNAPSHOT;
```
If the periodic snapshot background job is active, the result will return the path and the time at which the snapshots will be created.

<Tabs.Tab>

<Steps>

{<h3 id="empty-the-wal-directory" className="custom-header">Empty the `wal` directory</h3>}

  If you want to restore data only from the snapshot file, ensure that the
  `wal` directory is empty:

     1. Find the container ID using a `docker ps` command, then enter the container using:

      ```bash
      docker exec -it CONTAINER_ID bash
      ```
     2. Position yourself in the `/var/lib/memgraph/wal` directory and `rm *`

{<h3 id="stop-the-instance" className="custom-header">Stop the instance</h3>}

  Run the following command
  
  ```bash
  docker stop CONTAINER_ID
  ```

{<h3 id="start-the-instance" className="custom-header">Start the instance</h3>}

  You can start the instance with the backed up files in two ways.

  {<h4 id="option-1" className="custom-header">Option 1</h4>}

  You can start the instance by adding a `-v
  ~/snapshots:/var/lib/memgraph/snapshots` flag to the `docker run` command,
  where the `~/snapshots` represents a path to the location of the directory
  with the back-up snapshot, for example: 

  ```bash
  docker run -p 7687:7687 -p 7444:7444 -v ~/snapshots:/var/lib/memgraph/snapshots memgraph/memgraph
  ```

  If you want to copy both WAL and snapshot files start the instance by adding
  a `-v ~/snapshots:/var/lib/memgraph/snapshots -v ~/wal:/var/lib/memgraph/wal`
  flags to the `docker run` command, where the `~/snapshots` represents a path
  to the location of the backed-up snapshot directory, and `~/wal` represents a
  path to the location of the backed-up wal directory for example: 

  ```bash
  docker run -p 7687:7687 -p 7444:7444 -v ~/snapshots:/var/lib/memgraph/snapshots -v ~/wal:/var/lib/memgraph/wal memgraph/memgraph
  ```

  {<h4 id="option-2" className="custom-header">Option 2</h4>}

  The other option is to copy the backed-up snapshot file into the `snapshots`
  directory after creating the container and start the database. So the commands
  should look like this: 

  ```bash
  docker create -p 7687:7687 -p 7444:7444 -v snapshots:/var/lib/memgraph/snapshots --name memgraphDB memgraph/memgraph
  tar -cf - sample_snapshot_file | docker cp -a - memgraphDB:/var/lib/memgraph/snapshots
  ```
  The `sample_snapshot_file` is the snapshot file you want to use to restore the
  data. Due to the nature of Docker file ownership, you need to use `tar` to
  copy the file as STDIN into the non-running container. It will allow you to
  change the ownership of the file to the `memgraph` user inside the container.

  After that, start the database with:
  ```bash
  docker start -a memgraphDB
  ```
  The `-a` flag is used to attach to the container's output so you can see the logs.

  Once memgraph is started, change the snapshot directory ownership to the `memgraph` user by running the following command:
  ```bash
  docker exec -it -u 0 memgraphDB bash -c "chown memgraph:memgraph /var/lib/memgraph/snapshots"
  ```
  Otherwise, Memgraph will not be able to write the future snapshot files and will fail.

</Steps>

## Database dump

The database dump contains a record of the database state in the form of Cypher
queries. It’s equivalent to the SQL dump in relational DBs. 
Database dump preserves nodes, relationships, indexes, constraints and triggers.

You can run the queries constituting the dump to recreate the state of the DB as
it was at the time of the dump.

To dump the Memgraph DB, run the following query:

```cypher
DUMP DATABASE;
```

If you are using Memgraph Lab, you can dump the database, that is, the queries
to recreate it, to a CYPHERL file in the `Import & Export` section of the Lab.

## Storage modes

Memgraph has the option to work in `IN_MEMORY_ANALYTICAL`,
`IN_MEMORY_TRANSACTIONAL` or `ON_DISK_TRANSACTIONAL` [storage
modes](/fundamentals/storage-memory-usage).

Memgraph always starts in the `IN_MEMORY_TRANSACTIONAL` mode in which it creates
periodic snapshots and write-ahead logging as durability mechanisms, and also
enables creating manual snapshots.

In the `IN_MEMORY_ANALYTICAL` mode, Memgraph offers no periodic snapshots and
write-ahead logging. Users can create a snapshot with the `CREATE SNAPSHOT;`
Cypher query. During the process of snapshot creation, other transactions will
be prevented from starting until the snapshot creation is completed.

In the `ON_DISK_TRANSACTIONAL` mode, durability is supported by RocksDB since it
keeps its own
[WAL](https://github.com/facebook/rocksdb/wiki/Write-Ahead-Log-%28WAL%29) files.
Memgraph persists the metadata used in the implementation of the on-disk
storage. 

## Backup in multi-tenancy <sup style={{ fontSize: '0.6em', color: '#888' }}>Enterprise</sup>

With [multi-tenancy](/database-management/multi-tenancy), each database keeps
its own snapshots and WAL files, so you back up and restore each database
separately. This section covers the [data directory
layout](#data-directory-layout), how to [back up a
database](#back-up-a-database) and how long [snapshots are
kept](#keep-snapshots-long-enough-to-restore). To restore one database, see
[Restore a single database on
Kubernetes](#restore-a-single-database-on-kubernetes-enterprise).

The examples use a database named `customers`:

```cypher
CREATE DATABASE customers;
```

### Data directory layout

The default `memgraph` database keeps its files directly in the data
directory. Every other database has a directory under `databases/`, named
after the database's UUID, not its name:

```plaintext copy=false
DATA_DIRECTORY/
├── snapshots/            # default memgraph database
├── wal/
└── databases/
    ├── .durability/      # maps database names to UUIDs
    ├── memgraph/         # links back to DATA_DIRECTORY
    └── DATABASE_UUID/
        ├── snapshots/
        └── wal/
```

`DATA_DIRECTORY` is the value of the `--data-directory` flag:
`/var/lib/memgraph` by default, and `/var/lib/memgraph/mg_data` in the
[Memgraph Helm charts](/getting-started/install-memgraph/kubernetes).

To find the directory of a database, read the `database_uuid` field of
`SHOW STORAGE INFO ON DATABASE`:

```cypher
SHOW STORAGE INFO ON DATABASE customers;
```

The query also works on a [suspended](/database-management/multi-tenancy#suspending-and-resuming-databases-enterprise)
database. The name-to-UUID mapping is kept only in `databases/.durability`,
which Memgraph reads at startup, so look up the UUID while the instance is
running.

### Back up a database

Snapshots are the files to back up: each one holds a full copy of one
database. To back up a database:

1. Switch to the database and lock its data directory, so Memgraph doesn't
   delete snapshots while you copy them. `LOCK DATA DIRECTORY` locks only
   the current database.

   ```cypher
   USE DATABASE customers;
   LOCK DATA DIRECTORY;
   ```

2. Copy the files from `DATA_DIRECTORY/databases/DATABASE_UUID/snapshots/`
   to storage outside the instance, for example with
   [rclone](https://rclone.org/). Store them under the database name, because
   the UUID alone doesn't tell you later which database a snapshot belongs to.
3. Unlock the data directory:

   ```cypher
   UNLOCK DATA DIRECTORY;
   ```

To include changes made since the last periodic snapshot, run
`CREATE SNAPSHOT;` in the database before you lock it.

### Keep snapshots long enough to restore

Memgraph keeps only the newest snapshots of each database: 3 by default,
set with `--storage-snapshot-retention-count`. The count applies to every
database separately. Older snapshots are deleted, with the WAL files they
cover.

The local restore window is roughly the retention count times the snapshot
interval (`--storage-snapshot-interval`). With a snapshot every 5 minutes and
a retention count of 3, the oldest local snapshot is about 15 minutes old.

Snapshots on the instance's own volume are not a backup: they're lost with
the volume, and they age out quickly. Copy them off the instance on a
schedule that covers the point in time you might need to restore to.

## Restore a single database on Kubernetes <sup style={{ fontSize: '0.6em', color: '#888' }}>Enterprise</sup>

You can replace the data of one database with a snapshot while the other
databases on the instance keep serving queries. The steps work with the
standalone and the [high availability](/database-management/clustering/high-availability/setup-ha-cluster-k8s)
Memgraph Helm charts.

Before you start, you need:

- `kubectl` access to the namespace Memgraph runs in.
- A Memgraph user with the `DURABILITY` [privilege](/database-management/authentication-and-authorization/role-based-access-control)
  and access to the database you restore. Restoring into a new database
  also needs the `MULTI_DATABASE_EDIT` privilege and access to the
  `memgraph` database.
- In a high availability cluster, a connection to the MAIN instance. Run
  `SHOW INSTANCES;` on a coordinator to find it.

The charts name the pods and containers as follows, and both mount the data
volume at `/var/lib/memgraph`:

| Helm chart | Pod | Container | Data directory |
|---|---|---|---|
| Standalone (`memgraph`) | `RELEASE_NAME-0` | `memgraph` | `/var/lib/memgraph/mg_data` |
| High availability (`memgraph-high-availability`) | `memgraph-data-ID-0` | `memgraph-data` | `/var/lib/memgraph/mg_data` |

`RELEASE_NAME` is the Helm release name; if it doesn't contain `memgraph`,
the chart appends `-memgraph` to it. `ID` is the data instance's `id` from
the chart values. Check the exact names with `kubectl get pods`.

<Steps>

{<h3 id="find-the-databases-snapshot-directory" className="custom-header">Find the database's snapshot directory</h3>}

Get the database's UUID:

```cypher
SHOW STORAGE INFO ON DATABASE customers;
```

Its snapshots are in
`/var/lib/memgraph/mg_data/databases/DATABASE_UUID/snapshots/`. If the
database is suspended, resume it first; `USE DATABASE` on a suspended
database fails.

```cypher
RESUME DATABASE customers;
```

{<h3 id="choose-the-snapshot" className="custom-header">Choose the snapshot</h3>}

Where the snapshot is decides the path you pass to `RECOVER SNAPSHOT` in the
next step:

- **On the database's own volume:** switch to the database and list its
  snapshots. Use the `path` column as is.

  ```cypher
  USE DATABASE customers;
  SHOW SNAPSHOTS;
  ```

- **In S3-compatible storage:** use the `s3://` URL. See
  [S3-compatible storage](#s3-compatible-storage) for credentials.
- **On a server reachable over HTTP or FTP:** use the `http://`, `https://`
  or `ftp://` URL.
- **On your machine:** copy it onto the pod's data volume:

  ```bash
  kubectl exec -n NAMESPACE POD -c CONTAINER -- mkdir -p /var/lib/memgraph/restore
  kubectl cp -n NAMESPACE -c CONTAINER ./SNAPSHOT_FILE POD:/var/lib/memgraph/restore/SNAPSHOT_FILE
  ```

  `NAMESPACE` is the Kubernetes namespace, `POD` and `CONTAINER` are the
  names from the table above, and `SNAPSHOT_FILE` is the snapshot's file
  name. `kubectl cp` writes the file as the container's user, so Memgraph
  can read it. Use `/var/lib/memgraph/restore/SNAPSHOT_FILE` as the path.

{<h3 id="restore-the-snapshot" className="custom-header">Restore the snapshot</h3>}

You can restore over the existing database, or into a new database and
switch to it once you've checked the data.

In the examples, `SNAPSHOT_PATH` is the path or URL from the previous step.

Either way, Memgraph copies the snapshot into the database's
`snapshots/` directory and moves the files that were there to `.old`
directories (see [Usage of .old directory](#usage-of-old-directory)). Other
databases on the instance aren't affected.

In a high availability cluster, run `RECOVER SNAPSHOT` on MAIN. MAIN then
sends the restored database to every REPLICA. On a REPLICA, the query fails
with:

```plaintext copy=false
Failed to recover a snapshot. Replica instances are not allowed to create them.
```

{<h4 id="restore-in-place" className="custom-header">Restore in place</h4>}

Switch to the database and recover the snapshot with `FORCE`, which deletes
the database's current data first:

```cypher template
USE DATABASE customers;
RECOVER SNAPSHOT "SNAPSHOT_PATH" FORCE;
```

<Callout type="warning">
Memgraph keeps the database's previous snapshots and WAL files in `.old`
directories only until the next `RECOVER SNAPSHOT` on that database, which
deletes them. Copy them elsewhere first if you might need them.
</Callout>

{<h4 id="restore-into-a-new-database" className="custom-header">Restore into a new database</h4>}

A new database is empty, so it doesn't need `FORCE`, and the original stays
untouched:

```cypher
CREATE DATABASE customers_restored;
```

```cypher template
USE DATABASE customers_restored;
RECOVER SNAPSHOT "SNAPSHOT_PATH";
```

When the data is right, swap the two with
[`RENAME DATABASE`](/database-management/multi-tenancy#rename-database).
`RENAME DATABASE` doesn't move user and role access, so grant access to the
restored database again. The restored database keeps its own UUID, so after
the swap its files are in a different `databases/DATABASE_UUID/` directory
than before; point your backup job at the new one.

```cypher
RENAME DATABASE customers TO customers_old;
RENAME DATABASE customers_restored TO customers;
```

{<h3 id="check-the-result" className="custom-header">Check the result</h3>}

Switch to the restored database and check its contents, for example the
node and relationship counts in `vertex_count` and `edge_count`:

```cypher
USE DATABASE customers;
SHOW STORAGE INFO ON CURRENT DATABASE;
```

Once you no longer need the copied file, delete it:

```bash
kubectl exec -n NAMESPACE POD -c CONTAINER -- rm /var/lib/memgraph/restore/SNAPSHOT_FILE
```

</Steps>

### Restore when Memgraph doesn't start

If a database's files are damaged, Memgraph stops at startup and the pod
restarts in a loop. Add `--storage-allow-recovery-failure=true` to the
instance's flags (`memgraphConfig` in the standalone chart, the data
instance's `args` in the high availability chart) and upgrade the release.
The damaged database comes up empty in a broken state, the others start
normally, and you can restore it with the steps above. See
[recovery failure handling](/fundamentals/data-durability#recovery-failure-handling).

## Usage of .old directory

By default, Memgraph backs up durability files to `snapshots/.old` and `wal/.old` directories before operations that could risk data loss.

When backup occurs:

1. `RECOVER SNAPSHOT` query - Before loading an external snapshot, Memgraph moves existing files from `snapshots/` to `snapshots/.old` and from `wal/` to `wal/.old`. This
protects your data if the newly loaded snapshot turns out to be corrupted.
2. High Availability force sync - During replica's force syncing. See [this page](/database-management/clustering/high-availability/how-high-availability-works#replication-scenarios) for details.

Configuration:

Use the `--storage-backup-dir-enabled` flag to control this behavior:
- `true` (default) - Old durability files are moved to `.old` directories
- `false` - Old durability files are deleted immediately

## Best practices

Memgraph can optimize restoring of snapshots in a multi-threaded manner. To enable multi-threaded restoration of a snapshot, you need to ensure
the following flags are present:
- `--storage-parallel-schema-recovery=true`
- `--storage-recovery-thread-count=<number_of_cores>` where `number_of_cores` is the amount of CPU cores to parallelize the restoration process
